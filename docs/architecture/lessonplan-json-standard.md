# LessonPlan JSON Standard

## 1. Purpose

`LessonPlan` JSON is the core language of TeacherAI. Every explanation generated by AI must use this standard so lessons are teachable, reviewable, verifiable, renderable, voice-ready, animation-ready, video-ready, and reusable for future datasets and training.

This document is architecture and schema design only. It does not implement validation code, renderer code, AI prompts, provider adapters, or application business logic.

## 2. Core Rule

```text
AI Provider -> LessonPlan JSON -> Verification -> Renderer / Voice / Video / Review / Dataset
```

AI providers must output semantic lesson structure only. They must not output raw SVG, raw HTML, canvas commands, video instructions, arbitrary CSS, executable code, or provider-specific renderer commands.

Decision: LessonPlan JSON becomes TeacherAI's stable educational interchange format across AI engines, teacher review, student sessions, renderers, voice, video, datasets, and future model training.

## 3. Design Goals

- Support mathematics, physics, chemistry, biology, geometry, and future subjects without schema rewrites.
- Preserve pedagogical intent, not just answers.
- Support renderer-independent visual intent for whiteboard, PDF, images, and future video.
- Support voice narration, captions, timing maps, and future localization.
- Support future animation through semantic timeline hints, not imperative drawing commands.
- Support teacher comments, teacher corrections, student comments, and student misconception feedback.
- Support verification by math/science engines and teacher reviewers.
- Support dataset lineage and fine-tuning exports.
- Support accessibility, safety, versioning, and reproducibility.

## 6. Top-Level Blocks

| Block | Responsibility |
| --- | --- |
| `schema` | Identifies the LessonPlan standard and version. |
| `source_context` | Connects the lesson to question text, assets, OCR, student context, and teacher context. |
| `metadata` | Stores subject, topic, subtopic, difficulty, standards, objectives, prerequisites, and tags. |
| `learning_design` | Stores pedagogy strategy, scaffolding, misconceptions, and checks for understanding. |
| `content` | Stores lesson title, summary, ordered steps, content blocks, final answer, and practice prompts. |
| `verification` | Stores validation status and references to math/science verification reports. |
| `rendering` | Stores renderer constraints, render profiles, source mapping, and output artifact references. |
| `voice` | Stores narration policy, voice cues, transcript status, captions, and timing references. |
| `animation` | Stores semantic animation cues and timeline policies. |
| `video` | Stores future video-generation requirements and artifact references. |
| `comments` | Stores teacher comments, student comments, corrections, and review status. |
| `dataset` | Stores training eligibility, quality score, lineage, and exclusion reasons. |
| `safety` | Stores safety flags, age appropriateness, privacy, and moderation decisions. |
| `extensions` | Controlled extension point for future subjects or institutions. |

## 7. Subject Support

### 7.1 Math

Math uses `math_expression`, `graph`, `table`, and `geometry_diagram` content blocks.

Required support:

- LaTeX expressions.
- Step transformations.
- Equation references.
- Graph/table links.
- Verification references.

### 7.2 Physics

Physics uses `physics_expression`, `graph`, `table`, and explanatory text blocks.

Required support:

- Units and dimensions.
- Variables and constants.
- Formula selection.
- Free-body diagram descriptions through structured data.
- Experimental data tables.

### 7.3 Chemistry

Chemistry uses `chemical_equation`, `table`, `definition`, and process blocks.

Required support:

- Balanced equations.
- Mole ratios.
- Compounds, elements, states of matter, charges, and reaction conditions.
- Lab safety notes.

### 7.4 Biology

Biology uses `biology_process`, `definition`, `table`, `graph`, and diagram blocks.

Required support:

- Process sequences.
- Systems and relationships.
- Labels for diagrams.
- Cause/effect explanations.
- Vocabulary emphasis.

### 7.5 Geometry

Geometry can be represented as `geometry_diagram` plus `math_expression` blocks.

Required support:

- Points, lines, rays, segments, polygons, circles, arcs, angles, measurements, congruence, similarity, and parallel relationships.
- Diagram constraints rather than AI-authored coordinates.
- Proof steps and theorem references.

## 8. Content Block Standard

A content block is the smallest semantic instructional unit.

```json
{
  "block_id": "block_equation_1",
  "type": "math_expression",
  "text": "Start with the original equation.",
  "latex": "2x + 3 = 11",
  "structured_data": {
    "expression_role": "original_equation",
    "variables": ["x"]
  },
  "accessibility_text": "Two x plus three equals eleven.",
  "source_refs": ["ocr_region_r1"]
}
```

Decision: content blocks are semantic, reusable by verification engines, renderers, voice engines, teacher review, and datasets.

## 9. Renderer Contract

Renderer instructions are semantic intents, not drawing commands.

```json
{
  "rendering": {
    "render_profiles": ["whiteboard", "pdf", "thumbnail"],
    "preferred_layout": "step_by_step_whiteboard",
    "style_policy": {
      "theme": "teacherai_default",
      "handwriting_style": "clean_teacher_handwriting",
      "accessibility_mode": "standard"
    },
    "artifact_refs": []
  }
}
```

Render intents live at the step level and reference content block IDs:

```json
{
  "intent_id": "intent_arrow_1",
  "type": "arrow",
  "target_block_ids": ["block_equation_1", "block_equation_2"],
  "purpose": "show_equation_transformation",
  "style_hint": "teacher_guided"
}
```

Decision: the renderer decides SVG, PNG, JPEG/JPG, PDF, animated whiteboard, and future video details from these semantic intents.

## 10. Voice Contract

Voice is represented as narration policy and cue metadata.

```json
{
  "voice": {
    "enabled": true,
    "locale": "en-US",
    "voice_policy": {
      "style": "calm_teacher",
      "speed": "normal",
      "use_student_friendly_language": true
    },
    "caption_policy": {
      "enabled": true,
      "include_math_read_aloud": true
    },
    "artifact_refs": []
  }
}
```

Step-level voice cues:

```json
{
  "cue_id": "voice_cue_1",
  "type": "emphasis",
  "target_block_id": "block_equation_2",
  "spoken_text": "Notice that we subtract three from both sides, not just one side."
}
```

Decision: voice artifacts can be regenerated without changing lesson content.

## 11. Animation Contract

Animation cues are semantic and renderer-owned.

```json
{
  "animation": {
    "enabled": true,
    "timeline_policy": "step_sequential",
    "reduced_motion_alternative": true,
    "sync_with_voice": true
  }
}
```

Step-level animation cue:

```json
{
  "cue_id": "anim_cue_1",
  "type": "reveal_then_highlight",
  "target_block_id": "block_equation_2",
  "pedagogical_purpose": "focus_student_attention_on_inverse_operation"
}
```

Decision: LessonPlan JSON says what should be emphasized; the animation engine decides how to animate it.

## 12. Video Generation Contract

Video is a future downstream artifact generated from lesson content, renderer output, animation timeline, and voice artifacts.

```json
{
  "video": {
    "enabled": false,
    "future_generation_ready": true,
    "target_formats": ["mp4", "webm"],
    "caption_required": true,
    "thumbnail_policy": "auto_from_key_frame",
    "artifact_refs": []
  }
}
```

Decision: video generation must not create a separate lesson source. It must remain downstream of LessonPlan, Renderer, Animation, and Voice.

## 13. Teacher and Student Comments

Comments support review, improvement, and future datasets.

```json
{
  "comments": {
    "teacher_comments": [
      {
        "comment_id": "tc_001",
        "teacher_id_hash": "teacher_hash_91ab",
        "target": { "type": "step", "id": "step_2" },
        "comment_type": "correction",
        "text": "Use 'subtract from both sides' instead of 'move across the equals sign'.",
        "status": "applied",
        "created_at": "2026-07-26T00:00:00Z"
      }
    ],
    "student_comments": [
      {
        "comment_id": "sc_001",
        "student_id_hash": "student_hash_22ab",
        "target": { "type": "step", "id": "step_2" },
        "comment_type": "confusion",
        "text": "Why do we subtract 3 first?",
        "created_at": "2026-07-26T00:05:00Z",
        "privacy_status": "not_for_training_until_reviewed"
      }
    ]
  }
}
```

Decision: teacher comments can become high-quality correction data; student comments require privacy and review controls before training use.

```json
    "age_appropriate": true,
    "privacy_status": "redacted",
    "moderation_status": "passed"
  },
  "extensions": {}
}
```

## 15. Validation Rules

1. Every AI-generated explanation must be valid LessonPlan JSON before it can be rendered, voiced, shown to students, reviewed by teachers, or included in datasets.
2. Every content block must have a stable `block_id`.
3. Every step must have stable `step_id`, sequence, title, and content blocks.
4. Subject-specific data must live inside typed content blocks or controlled extensions.
5. Renderer information must remain semantic render intent, not drawing commands.
6. Voice cues must reference step or block IDs.
7. Animation cues must reference step or block IDs and describe pedagogical purpose.
8. Teacher and student comments must target stable lesson entities.
9. Training eligibility must default to false until verification, safety, privacy, and teacher approval gates pass.
10. The schema version must be preserved in every stored lesson.

## 16. Versioning Strategy

- Patch versions add optional fields only.
- Minor versions add backward-compatible block types or optional structures.
- Major versions may change required fields or semantics.
- Stored lessons keep their original schema version.
- Migration jobs create new lesson versions rather than mutating historical records.
- Renderers and voice engines declare supported LessonPlan schema versions.

## 17. Extension Strategy

Extensions are allowed only when the core schema cannot represent a legitimate subject requirement.

Rules:

- Extensions must be namespaced, for example `org.teacherai.advanced_chemistry`.
- Extensions must not override core fields.
- Extensions must include schema version and owner.
- Extensions must not contain executable code or renderer commands.
- Repeated extension patterns should be promoted into the core standard through an architecture decision record.

## 18. Implementation Guardrails

When implementation begins:

1. Build JSON schema validation before connecting any AI provider.
2. Reject AI output that is not valid LessonPlan JSON.
3. Reject AI output containing raw renderer commands or executable code.
4. Require Math/Science Verification before student playback for answer-bearing lessons.
5. Require Teacher Review before dataset training eligibility.
6. Keep render, voice, animation, and video generation downstream of LessonPlan JSON.
7. Use LessonPlan IDs, step IDs, and block IDs as source maps across renderer, voice, comments, analytics, and datasets.
8. Treat this standard as the core TeacherAI language and evolve it through versioned schemas and ADRs.
